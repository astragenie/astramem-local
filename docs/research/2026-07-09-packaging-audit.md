## Packaging 3 → 9 punch list

Ordered; each item is a specific file/change.

1. **[S] Fix `SECURITY.md` supported-version table** — bump `0.8.x` → `0.10.x` (or express as "latest release only"). One line, but it's actively wrong today and SECURITY.md is one of the first files a security-conscious adopter checks.
2. **[S] Fix README version staleness** — README.md:3 and README.md:508, `v0.8.1` → `v0.10.0`; while there, update the tool count from "15-tool" to "17-tool" (see item 4). Ideally source this from `package.json.version` via a doc-lint script so it can't drift again — CHANGELOG discipline is already good, README isn't wired to it.
3. **[S] Fix `docs/configuration.md` command names** — 7 occurrences of `astra-memory {init,doctor,service stop,service start,rebuild,reembed-dim}` → `astramem-local {...}` (lines 3, 12, 13, 44, 180, 183). Also fix the stale Windows path on line 10 (`%APPDATA%\AstraMemory` → `%APPDATA%\Astramem`, matching `src/config/datadir.ts:34` and CLAUDE.md).
4. **[S-M] Reconcile the MCP tool table** — add the 5 missing tools (`agent_profile`, `restore_memory`, `erase_memory`, `list_consolidation_proposals`, `resolve_consolidation_proposal`) to README.md's tools table (243-256) with their route mappings, matching the pattern of the existing 12 rows. Update the "17-tool" count everywhere it's asserted. Consider a CI check that asserts `registerTool(` call count in `src/mcp/server.ts` matches the row count in the README table — this has drifted three times already (12 → 15 → 17) without docs catching up.
5. **[S] Fix `docs/contracts.md:11`** — "frozen at migration 001-init" → either drop the specific number or say "frozen at the atom@2 contract cut (0.10.0), migrations continue independently" — the two are different axes (schema migrations vs. the public contract surface) and conflating them is what produced the stale claim.
6. **[S] Add `description` and `keywords` to `package.json`** — e.g. `"description": "Local-first, encrypted memory daemon for AI coding agents"`, keywords covering `mcp`, `claude-code`, `memory`, `rag`, `local-first`, `sqlite`. Cheap, directly improves npm/GitHub search surface.
7. **[S] Add badges to README** — npm version, license, and CI status badges at the top. Shields.io badges are static images/links, zero infra cost, and are the fastest visual "this is maintained" signal for a first-time visitor.
8. **[M] Windows/macOS CI runners** — carried over from the prior report, still open. `.github/workflows/test.yml` is Linux-self-hosted-only; README documents Windows/macOS as first-class (config paths, service adapters for all three OSes exist in `src/service/`). At minimum, add scheduled (not per-PR, to respect the self-hosted-only fleet policy) cross-platform smoke coverage, or document the gap honestly in README/CONTRIBUTING if GitHub-hosted runners are a hard no for this org.
9. **[M] Verify the plugin-repo blockers (B4)** — out of scope for this pass since it's a sibling repo, but it was flagged as a week-1 credibility blocker in the prior report and is still unverified. Needs its own audit pass before an OSS announcement that positions the plugin as the primary funnel (per the prior report's Deliverable 6, item 3).

## Product 8 → 9 punch list

3-5 items, adoption/credibility-blocking gaps only (not new features).

1. **[M] Publish a real retrieval-eval number, not just the CI floor.** The daemon's strongest differentiator (per the 2026-07-08 competitive analysis) is CI-gated retrieval quality, but the public-facing number is still just "recall@10 ≥ 0.9, NDCG@10 ≥ 0.7" floors against an in-repo fixture — not an external, comparable benchmark. `package.json` already has `eval:longmemeval:*` scripts wired up (`scripts/eval/longmemeval/`); running and publishing one honest LongMemEval/LoCoMo number (even mid-pack) is the single highest-leverage move identified in the prior report's Deliverable 4 (Month 1 plan) and directly targets the field's credibility crisis the report documents. This is now the top deferred item since every week-1 packaging blocker is otherwise resolved or near-resolved.
2. **[S-M] Demo/announcement asset showing `why_memory` as the differentiator.** The provenance receipt (`why_memory`) and event-sourced lifecycle are, per the competitive matrix, unique in the field — nothing in the repo today (no gif/asciinema/screenshot) shows it working. `astramem-local demo` (README, already shipped) is the right vehicle to script this from — low effort, high credibility payoff for an HN/launch audience.
3. **[S] Version-truth CI check.** The README version-staleness (N1) and MCP-tool-count drift (N2) are symptoms of the same root cause: nothing enforces that docs track `package.json.version` or the registered-tools count. A cheap lint step (grep-based, no need for anything fancy) in `.github/workflows/lint.yml` catching "README version string != package.json version" and "MCP tool count in README != registered tool count in server.ts" would prevent this exact class of embarrassment from recurring at the next 3 releases, given the project ships roughly one release per day right now.
4. **[M] Cross-platform install confidence.** Same underlying gap as packaging item 8 — the product's credibility claim ("first-class Windows/macOS/Linux") isn't backed by any automated evidence, only manual smoke (per the prior report). This is a product trust gap as much as a packaging one: an adopter on macOS/Windows has no CI signal that `init → reinstall → ingest → recall` actually works on their platform today.

## Top 3 do-first items

1. **Fix README's stale `v0.8.1` banner + tool-count claim (N1/N2, packaging items 2 & 4).** This is the literal first thing anyone lands on, it's provably wrong against the very `package.json` sitting next to it, and it's the highest-visibility instance of exactly the "fossilized README" problem the whole prior report was about — fixing it is minutes of work with outsized credibility payoff.
2. **Fix `SECURITY.md`'s wrong supported-version table (packaging item 1).** A security policy that's visibly two releases stale undermines the "independently security-audited this week with zero blockers" claim the prior report leads with — it's the kind of thing a careful reader (exactly the audience an OSS security story targets) checks first and notices immediately.
3. **Run and publish one honest external eval number (product item 1).** Every other week-1 packaging blocker from the prior report is now fixed or one small edit away; the eval-harness infrastructure (`eval:longmemeval:*` scripts) already exists and is unused publicly. This is the biggest remaining lever on the 7.9 → 8.4 competitive score the prior report identified, and unlike the doc fixes above, it's the one item that actually needs to happen before an announcement, not just before someone reads the README closely.
