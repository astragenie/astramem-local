# astramemory-local — Performance Baseline (2026-07-08)

Measurement-only pass. Harness under `scripts/perf/`; raw per-size JSON under
`.eval-data/perf/<N>/` (gitignored). No `src/` changes were made — findings
below are recommendations, not applied fixes.

## Machine

- CPU: Intel(R) Core(TM) Ultra 7 255HX × 20 logical cores
- RAM: 33.8 GB
- OS: Windows 11 (win32 10.0.26200)
- Node: v24.16.0, Bun: 1.3.14
- Daemon: `ASTRA_MEMORY_MOCK_PROVIDERS=1` (deterministic mock embeddings, dim=1024) for corpus seeding and endpoint benchmarks — real Ollama measured separately (embed-cost section). Encryption disabled (isolated eval sandbox, matches `scripts/eval/longmemeval` convention).

## Fusion micro-profile (direct DB calls, no HTTP/daemon — isolates FTS vs vec vs join cost)

30 iterations per size, `vecK=50` (matches `search()`'s default for limit ≤ 12). No src/ timing hook exists for this (only the `SearchDebugHit` score-breakdown projection, which is not wall-clock timing) — this script calls the same exported functions `search()` calls internally (`SqliteVecStore.search`, `fuseHits`, the FTS5 SQL) and times each directly.

## Is sqlite-vec linear? Where's the knee?

There is no knee — it's a straight line. VEC p50 scales **9.5×** for a 10× corpus increase (1k→10k) and **11.8×** for the next 10× (10k→100k): textbook O(N) brute-force scan. sqlite-vec's `vec0` virtual table has no ANN index (no IVF/HNSW) in this schema — `mv.embedding MATCH ? AND mv.k = ?` computes distance against every row, then takes the top-k. At 100k rows the vec scan (509ms p50) is essentially the *entire* cost of `GET /search` (469ms p50) and `POST /recall` (503ms p50) — FTS (30ms) and fusion (3.6ms) are noise by comparison. `fuseHits` itself stays flat and cheap at every size (only proportional to the ~50-candidate window, never to N) — it is not a bottleneck at any tested scale.

## Real embed cost (single query, mxbai-embed-large via Ollama, separate from the mock-provider numbers above)

n=8 calls, steady-state (model already resident): p50=156.5ms, p95=197.6ms, max=197.6ms, mean=136.5ms. A separate cold-start observation (model not yet loaded into Ollama) measured **~3970ms** for the first call, dropping to ~35-270ms once warm. **Add ~35-200ms to every `/search`/`/recall` row above to get real-world latency** (mock provider embeds in ~0ms, which is why the tables above under-report embed cost specifically) — with an outsized ~4s one-time tax on the first query after Ollama has evicted the model.

## Top-5 optimization candidates

1. **sqlite-vec brute-force KNN scan — the dominant cost at scale.**
   Evidence: VEC leg alone is 509ms p50 at 100k, vs. 30ms for FTS and 3.6ms for fusion — it *is* the `/search`/`/recall` latency at that size, and scales linearly with zero plateau across the tested range.
   Fix direction: no ANN index exists in the current sqlite-vec version/schema; options are (a) partition vectors so a query only scans a bounded shard (e.g., per-repo/per-project sqlite-vec tables, chosen when a hard filter is already present), or (b) push hard SQL filters (repo/project/agent/type) into a pre-filtered candidate set before the vector leg runs — currently blocked by `SqliteVecStore.search`'s own comment that `VecFilter` pre-filtering isn't implemented — or (c) upgrade to a newer sqlite-vec release if one adds real ANN indexing.
   Predicted gain: potentially 10-50× at 100k if the effective per-query scan set shrinks to a repo/project-sized shard instead of the whole table.
   Effort: **L** (schema/migration + re-embed + application logic; touches core retrieval).
   Risk: **M-H** — changes recall semantics; must be gated behind the existing ADR-005 retrieval-eval harness (recall@10/NDCG@10 floors) before shipping, not just a raw latency win.

2. **`GET /health` does an unindexed full scan of `memory_events` that grows with corpus size — surprising, since a health/liveness endpoint should be O(1).**
   Evidence: 21ms (1k) → 27ms (10k) → **1179ms p50 / 2352ms max** (100k). Root cause (confirmed in code): `usefulnessRate()` (`src/storage/usefulness.ts:168`) runs two `SELECT COUNT(DISTINCT atom_id) FROM memory_events WHERE event_type='usefulness' AND json_extract(payload_json,'$.family')=... AND created_at >= ?` queries on every `/health` call. The only index on `memory_events` is `(atom_id, seq)` (migrations/007, 013) — nothing covers `event_type`/`created_at`, and a `json_extract()` predicate can't use a plain B-tree index anyway. `memory_events` grows ~1:1 with memories created (`insertWithCreateEvent` logs one row per `/remember`), so this scan is genuinely O(N).
   Fix direction: same pattern this repo already used for the jobs table (migrations/018-jobs-distill-session-index.sql, which turned a full jobs-table scan into an indexed lookup) — add an index on `memory_events(event_type, created_at)`, and materialize the `family` value into its own column (small migration) so the WHERE clause can range-scan instead of evaluating `json_extract` per row.
   Predicted gain: likely brings `/health` back to single-digit ms at any corpus size (matching the precedent migration's effect).
   Effort: **S** — one migration, well-precedented in this codebase.
   Risk: **L** — additive index + one denormalized column, no behavior change.

3. **`GET /agents/:agent/profile` — missing index on `memories.agent`.**
   Evidence: 2.97ms (1k) → 8.98ms (10k, ~3×) → **236.94ms (100k, ~26× for the same 10× data growth — a cliff, not a line)**. Confirmed in code: `buildAgentProfile` (`src/server/queries/agent-profile.ts`) issues 4+ separate `WHERE agent = ? ...` queries (existence probe, per-type counts, first/last-seen, top-lessons, recent-decisions, corrections) against `memories`/`memory_events`, and `memories` has indexes on `(repo, type, created_at)` and `(session_id)` but **none on `agent`**.
   Fix direction: `CREATE INDEX idx_memories_agent ON memories(agent, valid_to, archived, type, created_at DESC)` (covering the `ACTIVE_CLAUSE` + type/created_at access pattern these queries already use).
   Predicted gain: likely 20-50× at 100k scale, bringing profile latency toward the sub-10ms range `why`/`digest` already show with their indexed paths.
   Effort: **S** — pure additive index.
   Risk: **L**.

4. **`POST /recall/pack` shows a disproportionate jump at 100k relative to its own 1k→10k trend.**
   Evidence: 4.77ms (1k) → 6.61ms (10k, ~1.4× for 10× data — sub-linear, healthy) → **86.43ms (100k, ~13× for the next 10× data)** — a clear inflection the 1k/10k numbers didn't predict.
   This is flagged with **lower confidence** than 1-3: `selectPack`'s repo/project/branch-scoped query should mostly ride the existing `idx_memories_repo_type` index, so the cause isn't yet pinned down from this pass — worth an `EXPLAIN QUERY PLAN` pass on `src/recall/pack.ts`'s query before committing to a fix (budget-based candidate trimming logic is a plausible suspect but unconfirmed).
   Effort: **M** (investigation first, then likely an index/limit tweak).
   Risk: **L**.

5. **`/search`/`/recall` tail latency (max) diverges more than p95 at 100k — weakest signal, needs more data before acting.**
   Evidence: `/recall`'s max (2714ms) is 2.4× its own p95 (1028ms) and notably worse than `/search`'s max (1162ms) despite `/recall` returning fewer hits (k=5 vs limit=10, and both use the same `vecK=50` window since `max(limit*4,50)=50` for both). This looks more like GC-pause/tail-variance noise in a single 150-iteration sample than a structural JSON-serialization cost, since the candidate/result set sizes are the same order of magnitude for both routes.
   Recommendation: re-run with more iterations (500+) and a flamegraph/clinic.js pass before treating this as an actionable optimization — listed for completeness, not as a confirmed lever.
   Effort: **S** (re-measurement) before any fix.
   Risk: **L**.

## Harness

- `scripts/perf/seed.mts` — seeds N memories via `POST /remember` (mock providers, concurrency 16) + a fixed 20-session enrichment batch; persists `.eval-data/perf/<N>/{datadir,manifest.json}`; skips reseeding if the manifest is already complete (`--force` to override); has a 20-minute wall-clock budget guard for the largest tier.
- `scripts/perf/bench.mts` — warm-daemon endpoint benchmarks (p50/p95/max/mean, configurable iterations/warmup).
- `scripts/perf/fusion-profile.mts` — direct-DB FTS/vec/fusion micro-profile. **Run under `node`, not `bun`** (`better-sqlite3` isn't supported under Bun's runtime — same footgun as the daemon itself); imports from `dist/`, so run `bun run build` first if stale.
- `scripts/perf/embed-cost.mts` — single-query real-Ollama embed latency, independent of the mock-provider corpus.
- `npm run perf:baseline` — runs the full sequence (seed → bench → fusion-profile → embed-cost) for the default `1000,10000,100000` sizes.
