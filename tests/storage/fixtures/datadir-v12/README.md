# datadir-v12 fixture (FEAT-420 / SLICE-414)

`memory.sqlite` is a small, plaintext (no cipher) SQLite datadir frozen at
migration version 12 (migrations 001-012 applied, 013-archival NOT applied).
It exists to prove the documented upgrade path (`git pull && bun run build &&
node dist/cli/index.js reinstall`) opens an old-schema datadir cleanly on the
current build with zero data loss — see
`tests/storage/upgrade-path.test.ts`.

Contents (10 deterministic memories, 4 entities, 10 memory_events, one
memories_vec row per memory) are described in `manifest.json`, which the test
asserts against after migrating the fixture to the current schema version.

The embedding dimension baked into this fixture's `memories_vec` table is 8,
NOT the production default (1024) — sqlite-vec's `vec0` virtual table
preallocates storage per chunk sized by `dim * 4 bytes`, so a small dim keeps
this committed binary small. The dimension is fully parameterized already
(FEAT-409); nothing about the upgrade path depends on 1024 specifically, and
`getVecSchemaDim()` always reads the real persisted dim rather than assuming
the default.

## Regenerating this fixture

Generated by `scripts/gen-upgrade-fixture.mts`, which re-implements
`migrate()`'s core apply-loop capped at a given version (no drift guard) so
it can freeze a DB at an arbitrary historical schema version, then seeds the
deterministic corpus defined in that script.

To regenerate after a deliberate change to the generator or its seed corpus:

```
bun scripts/gen-upgrade-fixture.mts --at 12 --out tests/storage/fixtures/datadir-v12
```

Commit the rewritten `memory.sqlite` and `manifest.json` together.
`tests/storage/upgrade-path.test.ts` re-runs the generator in-process and
asserts its manifest matches the committed one (anti-rot) — a content edit to
the generator that isn't matched by regenerating + recommitting fails CI.

## On a future schema bump (N -> N+1)

This fixture normally STAYS at v12 — its value is testing the oldest
realistically-supported upgrade path, not the newest. Only add a new
`datadir-vNN` fixture (don't replace this one) if a future slice specifically
decides the supported upgrade floor has moved forward; that is a product
decision, not a mechanical one, and should not happen as a side effect of an
unrelated migration landing.
