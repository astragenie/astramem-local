## FEAT-442 — Autonomous consolidation

**Architecture fit:** Sound extension of an already-well-designed pipeline. `consolidate.ts` already has a two-threshold shape (`mergeThreshold`/`proposeThreshold`) with winner selection (usefulness → importance → recency) and a containment auto-merge path that already auto-accepts without a human gate today. Adding a third confidence band that auto-accepts *proposal-tier* pairs above some higher-confidence cut only needs a new threshold parameter plus routing what is currently always-a-proposal into "auto-merge but log a distinguishing event." `mergeAsSupersede()` already event-sources through `MemoryEventRepo.supersede()`, which appends both a `supersede` event and a `memory_corrected` usefulness signal in one transaction — the provenance/audit trail the FEAT promises is mechanically already there for any call this feature would make. No schema migration is required to ship with the config knob defaulted off, matching the triage note.

**Real gap — reversibility is not implemented, and this is a bigger deal than the triage note implies.** I checked `MemoryEventRepo.restore()` directly: it throws `MemoryConflictError` unless `archived === 1`. A memory that was superseded via auto-merge is not archived — `valid_to` is set and `superseded_by` points at the winner, but `archived` stays 0. So `restore()` categorically cannot undo an auto-merge; there is no code path today that clears `valid_to`/`superseded_by` back to null for a superseded (non-archived) row. The FEAT's own triage note flags "no un-supersede primitive exists" as a scoped gap, but frames it as background — it is actually the load-bearing safety mechanism for the entire feature. Auto-accepting merges *without a human in the loop* and then discovering the confidence threshold was miscalibrated (a bad merge of two genuinely distinct facts) with no bulk way to walk it back is exactly the failure mode that would turn the "auditable and reversible" pitch into a liability. Today an operator's only recourse is hand-written SQL against `memories`/`memory_events`, which defeats the entire event-sourced design.

**Scope trap:** a builder could read "keep the human gate below the threshold" and treat that as the whole feature, shipping the auto-accept path without ever building the reversal primitive, because the FEAT text lists it as an "audit/reversal claim" rather than an acceptance criterion. Make it one explicitly.

**Recommended change before build:** add to this slice's scope (not a follow-up): an `unsupersede(atomId)` or `revertAutoMerge(eventId)` operation in `MemoryEventRepo` that reverses a specific `supersede` event caused by auto-accept (clear `valid_to`/`superseded_by`, restore `memory_entities` links, append a compensating event) — scoped narrowly to auto-accept-caused supersessions (identifiable via the event payload) so it doesn't have to solve reversal for every supersede path in the system.

**Sequencing:** no dependency on the other four FEATs. Independent, can run in parallel with anything else in this batch.

## FEAT-443 — Unix service parity

**Architecture fit:** Confirmed exactly as described, and the port is more mechanical than the FEAT text suggests. I traced `install-flow.ts`: on Windows it calls `writeShim()` (shim.ts) which writes a stable `astramemd.cmd` → `launch.cjs` → `current.json` pointer trio, and only the pointer is rewritten on upgrade. On every other platform, `install-flow.ts:82-84` falls straight to `taskExecPath = build.rawExecPath` — the absolute `"<node>" "<entryJs>"` string gets baked directly into the systemd unit's `ExecStart=` / launchd plist's `ProgramArguments` by `systemd.ts`/`launchd.ts`. Critically, `release.ts` (`materializeRelease`, `listReleases`, `pruneReleases`) is **already platform-agnostic** — it has no Windows-specific logic at all. This means the actual port is narrow: write a small stable launcher script (shell for systemd, or a thin wrapper plist-invokable script for launchd) that reads a JSON pointer file analogous to `current.json`, and repoint `install-flow.ts`'s non-Windows branch at that launcher instead of `build.rawExecPath`. The existing `restorePriorPointer`/`reinstall --rollback` logic in `src/cli/reinstall.ts` already operates on the pointer file abstractly enough that it should need only platform-specific path resolution, not new rollback logic. This is genuinely a "port a working pattern," matching the PM's own risk banding for that half of the FEAT.

**The watchdog half is a different animal, correctly flagged as such by triage.** I checked `task-xml.ts`: the Windows "watchdog" is not really a watchdog — it's a `PT5M` logon-trigger repetition on the scheduled task, with hang-detection actually happening implicitly through the `daemon.lock` instance-lock (a healthy re-run exits <100ms; a genuinely hung process holds the lock so the re-run just no-ops, and Windows Task Scheduler itself has no idea whether the daemon is "hung" vs "healthy," it just keeps re-triggering). There is no equivalent free lunch on systemd or launchd:
- **systemd** has a real primitive (`WatchdogSec=` + `sd_notify(WATCHDOG=1)`), but it requires the *daemon process itself* to periodically call `sd_notify` — new runtime code in the daemon's own event loop, not just a unit-file change. This is genuinely new surface, matching the PM's "no repo precedent, touches the daemon's own runtime loop" risk note.
- **launchd** has no watchdog-for-hangs primitive at all (`KeepAlive` only catches process exit/crash, not a wedged-but-alive process). The FEAT's own text says "timer-based re-exec" for launchd — that means building a small periodic launchd job that checks a heartbeat file/PID health and force-kills+relaunches, which is bespoke logic this repo has never needed before.

**Scope trap:** don't let "port the Windows architecture" imply the watchdog is symmetric across platforms — it is not, and a builder unfamiliar with `sd_notify`'s contract (daemon must call it, systemd doesn't poll) could ship a systemd unit with `WatchdogSec=` set but no corresponding `sd_notify` call in the daemon, which fails silently (systemd just never restarts, because it's still waiting for a heartbeat that never comes — arguably worse than no watchdog, since the operator believes one exists).

**Recommended change before build:** keep the PM's proposed SLICE-1/SLICE-2 split, but re-cut the boundary along pointer-indirection vs watchdog rather than Linux vs macOS — i.e. one slice does pointer-indirection + rollback for both systemd and launchd (the low-risk, well-precedented mechanical port), a second slice does the two watchdog implementations (systemd `sd_notify` + launchd heartbeat timer), which are unrelated enough in mechanism that bundling them by platform mixes a mechanical port with new-pattern work in the same review unit.

**Sequencing:** independent of the other four. No shared files with FEAT-442/444/445/446.

## FEAT-444 — Memory-health score

**Architecture fit — strong, but there is a direct collision with in-flight perf work that the FEAT evidence doesn't mention.** `docs/perf/2026-07-08-baseline.md` (same day's evidence set) identifies `GET /health` as an accidentally-O(N) endpoint: `usefulnessRate()` runs two unindexed `COUNT(DISTINCT atom_id)` scans over `memory_events` on every single call, measured at 1179ms p50 / 2352ms max at 100k rows. **Migration `019-health-agent-profile-indexes.sql` already exists in this repo and fixes exactly that** (partial covering indexes on `memory_events(created_at, atom_id) WHERE event_type='usefulness' AND ...family...`, plus `idx_memories_agent` for the agent-profile cliff). FEAT-444's AC-2 requires adding a `memory_health` detail block — junk rate, duplication rate, staleness distribution, poison/partial session counts — to that same `/health` response, on every call. If a builder computes those metrics the way `usefulnessRate()` was written (naive per-request aggregate queries with no index backing), this FEAT reintroduces the identical class of regression migration 019 was written to close, in the same endpoint, in the same week. Duplication-rate is a particular risk: the FEAT description says it reuses "consolidation similarity," but `consolidate.ts`'s own docstring explains why it caps group size at 500 — it's an O(n²) pairwise cosine scan per (repo,type) group. Running anything resembling that inline on a hot health-check path at 100k memories would be far worse than the bug just fixed, not a repeat of it.

**Recommended change before build:** the CLI report (AC-3) and the doctor row (AC-1) can afford real computation — they're operator-invoked, off the hot path, and read-only per the AC. The `/health` block (AC-2) should either (a) surface only pre-computed/cached summary numbers refreshed on an interval (matching the `worker.lastTickAt`/health-state pattern already in `health.ts`), or (b) be explicitly scoped to counts that ride existing or migration-019 indexes only (cheap aggregate counts), with duplication-rate and any LLM-judged sample excluded from the `/health` surface and reserved for the CLI/doctor paths. AC-2 as literally written ("the JSON response includes a new memory_health detail block") doesn't preclude a cheap-subset design — but it also doesn't rule out a naive one, so this needs to be an explicit instruction to the builder, not left implicit.

**Minor doc-accuracy issue, worth a one-line correction before dispatch:** AC-1 cites `CheckResultWithName` as "defined in `src/doctor/types.ts`" — I confirmed that type is actually defined in `src/doctor/runner.ts:3`; `types.ts` only has the unqualified `CheckResult`/`Check`. Trivial to fix, but worth catching now so a builder doesn't waste a cycle looking for it in the wrong file.

**Sequencing:** should land *after* migration 019 is merged (confirm it's not still pending review — it's present on disk as of this review but I did not check its migration-applied/CI status). If 019 is still in-flight in a parallel slice, FEAT-444 and that slice touch adjacent concerns (`memory_events` indexing, `/health` route) closely enough that they should not run as concurrent worktrees without coordination — same file (`src/server/routes/health.ts`) is a plausible touch-point for both.

## FEAT-445 — Single-binary spike (bun compile)

**Architecture fit — the spike is correctly scoped as a timeboxed report, but it is aimed at the wrong first question.** The FEAT frames the risk as "native modules + migrations/dist file layout" — a *bundling* risk (can `bun build --compile` embed/ship `.node` addons alongside a single executable). I found stronger, more fundamental evidence in this repo that the problem may not be bundling at all: `docs/perf/2026-07-08-baseline.md` states plainly that `better-sqlite3` "isn't supported under Bun's runtime — same footgun as the daemon itself," and `scripts/eval/extraction-bench/README.md:112-117` independently confirms the same thing from a different angle (a throwaway budget tracker in that toolchain deliberately uses `bun:sqlite` instead of `better-sqlite3-multiple-ciphers` specifically because "per CLAUDE.md, better-sqlite3 (multiple-ciphers included) is not supported under Bun, and this whole toolchain runs under bun"). If that's accurate as a *runtime* limitation (not just a missing-prebuild build-time issue), then `bun build --compile` — which produces a Bun-runtime executable — may be fundamentally incompatible with this daemon regardless of how cleverly native modules are bundled, because the compiled binary would still be Bun's engine trying to load `better-sqlite3-multiple-ciphers` at runtime. That would make this a same-day "never" rather than a day-long bundling investigation, and none of the FEAT text, the PM review, or the supermemory-matrix evidence doc surfaces this distinction — they all frame it as a packaging/bundling risk, one level shallower than where the actual landmine likely sits.

**Recommended change before build:** re-sequence the spike's own steps so the cheapest, most falsifiable check runs first: does `better-sqlite3-multiple-ciphers` load at all under plain `bun run <script-that-requires-it>` (no compile, no bundling) on this platform? That's a five-minute check that could end the spike immediately with a clear "never" (native module fundamentally unsupported under the Bun runtime) rather than spending the timebox exploring `--compile`'s bundling flags for a runtime that can't load the dependency in the first place. If it does load under plain `bun run` (worth confirming rather than assuming from the existing notes, since those notes may be about an older Bun version or a different code path), *then* proceed to the bundling/packaging questions the FEAT currently leads with.

**Sequencing:** independent, lowest blast radius in the batch (PM review already notes this correctly) — fine to run any time, including in parallel with the rest.

## FEAT-446 — SaaS SDK growth (memory repo, cross-repo)

**Architecture fit — the FEAT's central premise ("one SDK, two baseURLs") is in tension with a division of labor the tri-repo-plan document already settled this same day.** I read the actual SDK code: `memory/packages/astramem-sdk/src/index.ts` is unambiguously SaaS-shaped — `AstramemClientOptions.baseUrl` defaults to `https://app.astramemory.com/api`, and every request/response type (`CreateMemoryRequest.project_id/scope/agent_id`, `SearchRequest.metadata_filter/mode`, `SearchResultItem.rank_score/confidence_score`) matches the SaaS API's field vocabulary, not the daemon's (`repo`/`type`/`agent`/`session_id`, wire-versioned envelopes). Meanwhile `docs/research/2026-07-08-tri-repo-plan.md` (same evidence set this FEAT cites) already decided: *"plugins-common/astramem-client is where plugin provider/wire-probe/HTTP-client logic migrates over time... memory repo's @memoryservice/plugin-contracts + plugin-sdk are duplicates to retire onto the above."* I confirmed `plugins-common/packages/astramem-client/src/daemon-client.ts` already exists and is exactly the daemon-facing client the tri-repo plan designates as the long-term home for this logic. FEAT-446 proposes growing the *memory repo's* `astramem-sdk` to also speak the daemon's wire shape ("the daemon-compatible subset aligned with @astragenie/astramem-client so one SDK story targets both baseURLs") — that's a second daemon-client implementation living in the SaaS repo, which is structurally the same "written twice, never reconciled" problem the tri-repo plan is actively trying to kill one level down (it already flagged `@memoryservice/plugin-contracts` as exactly this kind of duplicate). Building it here would create a third client package (SaaS SDK, plugins-common client, and now a daemon-aware SaaS SDK) rather than converging toward the two the plan settled on.

I also checked whether the SaaS API has server-side support for the SDK-growth targets: `EntitiesController.cs` and `DecisionsController.cs` exist, so growing the SDK to cover entities/decisions against the SaaS API is legitimate. There is no `SessionDigestController`/equivalent anywhere in the SaaS controller set — session digest is a daemon-only concept (`GET /sessions/:id/digest`). So the FEAT's "session digest" SDK method can only be daemon-facing, which is exactly the dual-backend design that collides with the tri-repo plan's split above.

**Verdict rationale (needs-design-first, not proceed-with-changes):** this isn't a scope tweak — it's an open architectural question (which package owns daemon-client logic, and does one SDK package legitimately need two backend wire shapes internally, or should the SaaS SDK stay SaaS-only and daemon-facing growth happen in `plugins-common/astramem-client` instead) that should be resolved as a short design/ADR step before a builder starts writing SDK methods, or the `sdk-v1` tag — described in the FEAT itself as the FEAT's own irreversible terminal step, matching the triage note's `technical_risk=0.85` banding — risks locking in a published surface that the very next month's convergence work (Month 6 in the ecosystem report: "extract contracts/ into a shared package... one SDK targeting daemon and cloud") would have to break or deprecate almost immediately.

**Recommended change before build:** split the "grow methods against the SaaS API" work (entities/decisions/session-digest-for-SaaS-if-it-exists, low risk, clear server-side backing) from the "daemon-compatible subset" work (blocked on the design question above) so the low-risk half isn't held hostage by the unresolved one. Do not tag `sdk-v1` until that design question is answered — a wrong-shaped first tag is exactly the kind of hard-to-reverse public action the PM's own risk banding is warning about.

**Sequencing:** cross-repo (memory repo), and per the PM's own triage note, this loop cannot execute it directly regardless of the design question. Flag for human/architect resolution before any slice work, independent of FEAT-442-445 timing.

## Top 3 risks across the set

1. **Two FEATs quietly assume mechanisms this repo doesn't have yet, and both assumptions are wrong in the same way — described as "supporting infrastructure" rather than "missing infrastructure."** FEAT-442 calls auto-merge "reversible" when no un-supersede primitive exists (`restore()` explicitly refuses non-archived rows); FEAT-446 calls its target "one SDK, two baseURLs" when the daemon-facing half already has a different, tri-repo-plan-designated home. Both need their own real content added to scope (a reversal primitive; a design decision) rather than being treated as a detail to fill in during the build.

2. **FEAT-444 (memory health) and the just-landed migration 019 are two halves of the same perf story that the FEAT text doesn't connect.** Both touch `/health`'s cost profile; without an explicit instruction to keep the new `memory_health` block cheap/cached, a builder following the AC literally (add a detail block to every `/health` response) can reintroduce the exact O(N) full-scan bug migration 019 exists to fix, on the same endpoint, in the same week.

3. **FEAT-445's risk framing is one layer too shallow, and it changes the shape of the spike, not just its findings.** The evidence available in-repo (`docs/perf/2026-07-08-baseline.md`, `extraction-bench/README.md`) suggests `better-sqlite3-multiple-ciphers` may not run under the Bun runtime at all, which is a different (and cheaper-to-answer) question than "can `bun build --compile` bundle native addons." Ordering the spike to check that first could turn a 1-day investigation into a same-day "never" — worth doing regardless of which answer comes back, since it's strictly cheaper information.

None of the five FEATs share a file-level conflict with each other (service/, consolidate/, health+doctor/, package.json-spike, and cross-repo SDK are five disjoint surfaces), so they can build in parallel worktrees once the above changes are folded into each FEAT's scope — the sequencing constraints above are about correctness/design order within each FEAT, not contention between them.
