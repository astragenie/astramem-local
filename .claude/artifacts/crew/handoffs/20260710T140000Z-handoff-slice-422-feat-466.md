**Finding 1 (HIGH, fixed) — rollback to a pre-FEAT-466 binary could resolve
a stale or hard-coded-default bearer.** Root cause: `secrets.env` was only
written when the OS-store write failed, and the legacy OS-store identity
was never refreshed by the new scoped-write path, so a pre-FEAT-466
binary's resolution order (OS store *before* secrets.env — confirmed via
`git show c947310:src/storage/bearer-keystore.ts`) could land on a stale
value or the `'devtok'` default after a `token rotate` on the new binary.

Design decision applied (per team lead, org-level): **secrets.env is now
unconditionally authoritative for the bearer.**

- `storeBearer()`/`rotateToken()`'s `stored ? undefined : token` conditional
  is removed — `secrets.env` always gets the current `MEMORY_BEARER=` line
  in both `init.ts` and `token.ts`, regardless of OS-store success.
- `storeBearer()` gained an opt-in `{ writeThroughLegacy: true }` (new
  `StoreBearerOpts`), used ONLY by `token.ts`'s `rotateToken()` — it
  best-effort writes the rotated token into the legacy unscoped OS-store
  identity too, so a rolled-back pre-FEAT-466 binary (which reads that
  identity directly, no scoping concept) picks up the current token instead
  of a stale pre-upgrade one. `init.ts` deliberately does NOT set this flag
  — writing the legacy identity from a sandboxed/test `init` is exactly the
  mechanism that caused the original incident this FEAT closes.
- Never triggered under the `ASTRA_MEMORY_TEST_FORCE_KEYFILE` bypass (that
  path skips the OS store entirely, scoped and legacy alike).

**Finding 2 (hardening, fixed) — configDir normalization before hashing.**
`scopedService()` now runs `configDir` through a new `normalizeConfigDir()`
(`path.resolve` + trailing-separator strip + Windows case-fold) before
hashing, so `C:\Users\x`, `c:\users\x`, `C:/Users/x`, and a
trailing-backslash variant all hash to the same identity. Not a live bug
(every real call site already routes through the single `defaultConfigDir()`
function) but cheap defense-in-depth per the reviewer's recommendation.

## Objective

Close the 2026-07-10 incident where a sandboxed `init` overwrote the
production daemon's bearer in Windows Credential Manager: the OS
credential-store identity in `src/storage/keystore.ts` was fixed and
machine-global (service `astramem-local`, account `bearer`/`db-key`),
unscoped by APPDATA/configDir sandboxing, so any two installs on the same
machine collided on the same entry.

## What changed

- **Scoped credential-store identity** (`src/storage/keystore.ts`): new
  `scopedService(configDir)` computes `astramem-local:<sha256(configDir)
  .slice(0,16)>`. Both `getOrCreateKey()` (db-key) and `storeBearer()`/
  `readBearer()` (bearer) now write to this scoped identity, with a
  **read-only** fallback to the legacy unscoped identity (`astramem-local`)
  when the scoped one has nothing — no migration write, so old and new code
  can coexist without a re-init.
- **`ASTRA_MEMORY_TEST_FORCE_KEYFILE` extended to the bearer**: previously
  only gated the db-key's file fallback; now `storeBearer`/`readBearer` also
  honor it, writing/reading `<configDir>/bearer.key` (0600 + Windows ACL via
  the existing `restrictKeyFileAcl`) and never constructing an OS credential
  Entry at all when set.
- **`getBearerIdentity(configDir)`** (new export): reports `'scoped' |
  'legacy' | 'key-file' | 'none'` for doctor.
- **Doctor** (`src/doctor/checks.ts`): "Encryption at rest" and "Bearer
  token location" checks now append `identity: scoped|legacy` to their
  messages.
- **Call-site threading**: `storeBearer()`/`readBearer()` now require a
  `configDir` argument (previously implicit/global). Updated `init.ts`
  (already had `configDir` in scope), `token.ts` (`rotateToken` gained an
  optional `configDir` param, defaults to `defaultConfigDir()`),
  `bearer-keystore.ts` (`ResolveBearerOpts.configDir`, defaults to
  `defaultConfigDir()`).

attempts to talk to the real store.
