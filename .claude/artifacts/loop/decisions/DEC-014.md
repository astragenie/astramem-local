# DEC-014: The FEAT-458 bake gate blocks production ENABLEMENT of capture, not DEVELOPMENT of it

## Context

FEAT-458 (LLM proxy auto-capture) carries a runtime bake gate: 14 days of
FEAT-455 hook-tap capture running in production without rollback, plus ≥1 real
scrub-evidence instance, plus FEAT-463 shipped.

Two documents disagree on what that gate blocks:

- **ADR-013** (the FEAT's own security ADR, Accepted) says FEAT-463 must be
  shipped and closed *"before the capture fork **goes live in production**"*
  (Information Disclosure row, Decision 6). It gates **deployment**.
- **FEAT-458's `triage_notes`** say *"the gate that must clear before
  **building** is a RUNTIME condition."* It gates **implementation dispatch**.

The reviewer of the S2 branch applied the stricter (FEAT-458) reading and
rendered `incomplete_wip` on that basis, which blocks all implementation.

Two facts make resolving this urgent rather than academic:

1. **The bake has been accruing nothing.** Auto-capture has been ON in
   production since 2026-07-10 and has captured **0 memories** — verified
   2026-07-12 via `doctor` (`auto-capture is ON — 0 auto-captured memories
   currently stored`) and confirmed by `ingest.log`, which is full of
   `transcript file not found`. The capture-at-close fix is merged to source in
   both plugins but was never released, so every installed hook still runs the
   legacy deferred path. The ≥1-scrub-evidence condition was never going to be
   satisfiable, and the 2026-07-24 date would have arrived with the gate red.
2. Under the strict reading, ~6–9 dev-days of implementable work sits idle
   during a bake window that is itself not accruing.

## Decision

**The bake gate blocks turning proxy capture ON in production. It does not
block developing it.**

Permitted during the bake:
- S1 backfill: bench harness, design-gate artifact, doctor WARN row, disable→purge wiring.
- S2 finish: rebase, latency evidence, fresh review, merge.
- S3 development: the capture fork, behind a default-OFF flag, with its tests.
- S4 development: hardening, failure-mode matrix.

Forbidden until the gate genuinely clears:
- Enabling proxy capture in the **production** daemon config.
- Any default-ON capture flag reaching a released artifact.

Rationale: ADR-013 is the security authority here and it says "goes live in
production." The FEAT's triage note is a summary of the ADR, and where a summary
contradicts its source, the source wins. Nothing about writing a capture fork
behind an off-by-default flag exposes the disclosure risk ADR-013 is protecting
against — that risk is realized on *enablement*, when real traffic carrying real
system prompts and a real upstream API key starts transiting the tap.

## Consequences

- Development of S1–S4 may proceed in parallel with the bake clock. This is what
  makes a parallel implementation session possible.
- The gate must still be *honestly* satisfied before production enablement, and
  it currently is NOT and cannot be until the plugin releases land (astramem-plugin
  0.6.2, runner-plugin 0.72.0) and capture is observed actually capturing.
- Per operator decision 2026-07-12, once capture is confirmed working the bake
  will be **restarted and shortened** (the original 14 days was "accepted as
  drafted," not a derived number — ADR-013's own open-questions section asked
  whether 14 was right and the operator accepted it without deriving it).
- The `incomplete_wip` verdict on the S2 review is superseded on this point
  only. Its substantive findings (missing S1 deliverables, unmeasurable
  S2-AC-4 latency evidence with no bench harness) stand and must still be closed.

## Status

Accepted 2026-07-12 by operator decision, to unblock parallel proxy development
while the stable promotion proceeds independently of the proxy.
