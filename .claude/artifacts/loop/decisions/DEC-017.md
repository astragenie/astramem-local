# DEC-017 — Trust policy for string-derived project/repo identity when the worktree is deleted

## Decision

When the daemon must derive a memory's `project`/`repo` identity from a
client-sent `cwd`/`project_id` string and `git` cannot answer (the most
common case is the worktree already having been deleted by the time ingest
or backfill runs), the following policy applies:

1. **Trust boundary stays narrow.** A string-derived value is **TRUSTED**
   only for the two tool-generated layouts the loop harness itself produces:
   `<repo>/.claude/worktrees/<x>` and `<repo>-worktrees/<x>`. Any other
   unresolvable path shape stays `unresolved` — the FEAT-484 never-guess
   guard (`src/tag-hygiene/repo-identity-backfill.ts:19-26`) is preserved,
   not loosened. No new "assume the usual repo" fallback is introduced.
2. **Override is conservative, not blanket.** Ingest overrides a
   client-sent `project_id` **only when it equals `basename(cwd)`** — i.e.
   only the hook-produced shape (`PROJECT_ID="$(basename "$CWD")"`) is
   re-derived. An explicit, deliberately different `project_id` label is
   stored **verbatim** and never clobbered (FEAT-553 AC-5).
3. **Every override is observable, never silent.** Each override /
   re-stamp emits a structured log event carrying the original value, the
   derived value, and a `source` field of either `'git-common-dir'` or
   `'string-heuristic'` (FEAT-553 AC-7). Any filesystem location named in
   that event — or in backfill preview output — appears as the repo-root
   **basename**, never as an absolute path, matching the existing
   `src/redact/` posture (FEAT-553 AC-9).
4. **`repo` gets parity with `project`.** When `git` is unresolvable, `repo`
   receives the same string-heuristic fallback as `project` instead of
   being left `unresolved` — closing the half of FEAT-484 that only ever
   updated `project`/left `repo` short-changed in that scenario.

## Why

FEAT-484 (closed 2026-07-17) fixed repo-identity resolution for *live*
worktrees by preferring `git rev-parse --git-common-dir` over the cwd
basename. FEAT-425 (closed 2026-07-09) made the cwd-basename *fallback*
itself worktree-safe, but only for the `<name>-worktrees/<x>` sibling
convention — it predates Claude Code's nested `.claude/worktrees/agent-<id>`
layout and never needed to reason about a worktree that no longer exists on
disk, because it was a string-only heuristic to begin with.

FEAT-553's 2026-11-05 audit found the gap those two decisions left open: by
the time a transcript is captured, distilled, or backfilled, the worktree
directory is routinely already deleted (Claude Code tears it down when the
agent finishes) — so `git` can never answer, and the daemon has only the
string the client sent. Without a trust boundary, "derive something
plausible from a string" risks exactly the failure mode FEAT-484's
never-guess guard was written to prevent: a wrong-but-confident repo label
that silently merges two unrelated projects' memories under one identity.
This decision is the explicit boundary: trust the two tool-generated shapes
the loop harness actually produces, stay `unresolved` for everything else,
and make every re-stamp auditable rather than invisible.

## How to apply

- SLICE-444 (daemon ingest hardening + `deriveWorktreeSafeBasename`
  extension) and SLICE-445 (backfill extension to `project` + `sessions`)
  implement this policy — cite this DEC in both slices' handoffs rather than
  re-deriving the trust boundary from scratch.
- PM/triage: any future proposal to widen the trusted-shape set (point 1)
  or to override on anything looser than `project_id === basename(cwd)`
  (point 2) must supersede THIS decision first, not quietly drift past it.
- Reviewer ladder for SLICE-444/445: verify the override log event (point 3)
  always carries `source` and a basename-only path, and that `repo` (point
  4) is populated alongside `project` in the same pass, not a follow-up.
