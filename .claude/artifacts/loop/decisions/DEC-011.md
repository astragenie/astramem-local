# DEC-011: secrets.env is unconditionally authoritative for the bearer; rotate write-throughs legacy identity

## Context

FEAT-466 scoped the OS credential-store identity per configDir to stop
sandboxed `init` runs from clobbering the production bearer (2026-07-10
incident). Review found the scoping created a rollback trap: a pre-FEAT-466
binary reads the legacy unscoped OS identity BEFORE secrets.env, and the
pre-existing SEC-10 design only wrote MEMORY_BEARER= to secrets.env when the
OS-store write failed — so upgrade → rotate → rollback resolved a stale
bearer, or fell through to the hardcoded 'devtok' default on fresh installs.

## Decision

We will treat `secrets.env` as the unconditional source of truth for the
bearer: every bearer write (init, rotate) writes MEMORY_BEARER= to secrets.env
regardless of OS-store success; the OS credential store is a secondary copy.
Additionally, `token rotate` — and only rotate — write-throughs the new bearer
into the legacy unscoped OS identity (documented AC-2 exception), because a
rolled-back binary consults the OS store first. `init` never writes the legacy
identity: a sandboxed init writing it is exactly the incident mechanism.

## Consequences

- positive: rollback past the scoping release is safe including post-rotate;
  'devtok' fall-through is impossible post-rotate; repo docs' contract
  ("secrets.env contains MEMORY_BEARER") is now actually true unconditionally
- negative: bearer persists in plaintext file even when the OS store works
  (accepted — the file already held it in the common failure path and is the
  documented recovery mechanism); rotate touches a machine-global OS entry
  (contained: only the explicit `token rotate` CLI path, never automated)
