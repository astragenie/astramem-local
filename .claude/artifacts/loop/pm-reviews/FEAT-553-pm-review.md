## Scope Challenge

- **Scope notes:** SCOPE CORRECTION (verified, affects slicing): FEAT-553 scope item (a) says 'extend deriveWorktreeSafeBasename to handle .claude/worktrees/<x>' as if the repo leg were unfixed. It is not - FEAT-484 already resolves repo via git-common-dir, and src/tag-hygiene/repo-identity.ts:5-15 documents the exact .claude/worktrees/<x> gap the FEAT describes. The genuinely unfixed legs are (i) project, which bypasses all derivation because the client sends it verbatim, and (ii) the string-only fallback for worktrees ALREADY DELETED, where git cannot answer and resolveRepoIdentity returns null. Extending the string heuristic is therefore NOT redundant - it is the only mechanism that can recover identity for a deleted worktree from the recorded sessions.cwd alone, which is likely most of the 17,877 rows. Build it first; both the ingest override and the backfill depend on it.

ACCEPTANCE CONFLICT (resolve before slicing): the FEAT's criterion 'no memory or session row has project or repo matching ^agent-[0-9a-f]{17}$ after backfill' is UNACHIEVABLE under the existing design. src/tag-hygiene/repo-identity-backfill.ts:19-26 states as a deliberate migration hazard that a row whose cwd no longer resolves is 'left untouched and reported unresolved - there is no assume-its-the-one-repo-this-daemon-usually-serves fallback, because that would risk merging an unrelated memory into the wrong repo's consolidation group.' Driving the count to literal zero means either breaking that never-guess guard or recovering identity from the cwd string. My AC-8 asserts the honest form instead: the remaining count equals the reported unresolved count, with every remainder explicitly accounted for.

## Risks

- PRE-MORTEM 1 - two weeks later this failed review or validation, most likely cause: the backfill resolved far fewer rows than expected and the slice was marked done against an unmet acceptance criterion. src/tag-hygiene/repo-identity-backfill.ts resolves via resolveRepoIdentity, which spawns git against each row's recorded cwd; worktrees under .claude/worktrees/agent-<id> are deleted when the agent finishes, so for most of the 17,877 rows git returns null and the row is reported unresolved by design. If the string-heuristic path (SLICE-1) is not landed and wired into the backfill BEFORE the apply, the honest outcome is a near-total no-op that still reports success. Mitigation: AC-8 ties the remaining count to the reported unresolved count, and SLICE-1 is sequenced first.
- PRE-MORTEM 2 - this merged and broke the loop, what rollback actually requires: NOT git revert. Code changes revert cleanly, but once --yes has mutated 17,877 memories.project values and the corresponding sessions rows, the prior values are gone unless the backfill persists them. Re-stamping project also changes consolidation grouping keys - src/tag-hygiene/repo-identity-backfill.ts:28-31 exposes joiningExistingCount specifically because re-stamped rows join other rows' consolidation groups, and docs/memory.md records 2,131 consolidation proposals already backed up behind the dead sync token, so a 17,877-row re-group could multiply that queue. Rollback therefore needs either a pre-apply datadir backup or a recorded old-value journal, plus a consolidation-proposal cleanup. Require one of those before SLICE-6.
- PRE-MORTEM 3 - which existing test would NOT catch a regression here: none of the FEAT-425 cwd-basename cases, because they only assert the sibling <name>-worktrees/<x> convention and the unchanged-passthrough case (src/pipeline/cwd-basename.ts:20-22 documents that contract), so a nested .claude/worktrees/<x> input silently falls through to the raw basename today and would keep doing so. Equally, no test covers the client-sent project_id path at all - src/server/routes/ingest.ts:468 writes data.project_id verbatim, and the FEAT-484 worktree-ingest canary asserted on repo, not project. The slice's ACs must add a nested-worktree case to the cwd-basename suite and a project-column assertion to the ingest canary; without both, the exact bug reappears on the next convention change.
- SHARED-HELPER BLAST RADIUS: src/pipeline/cwd-basename.ts is imported by BOTH src/pipeline/derive-project.ts:1 and src/tag-hygiene/derive-repo.ts:1. Widening deriveWorktreeSafeBasename changes repo derivation too, so it can regress the already-shipped FEAT-484 and FEAT-425 behavior for any cwd containing a worktrees segment. The FEAT-425 AC-2 conservative-passthrough and AC-3 string-only (no git, no fs.stat) contracts must both be re-asserted by test, not merely preserved by intent.
- FULL-SCAN RUNTIME AT PROD SCALE: the existing backfill pulls every non-blank-repo row (SELECT id, repo, session_id FROM memories WHERE repo IS NOT NULL ORDER BY created_at ASC) and regex-filters in JS because SQLite has no portable REGEXP, then per candidate runs a sessions lookup, a COUNT(*) over memories, and potentially a git spawn whose cwd cache caps at 500 entries (src/tag-hygiene/repo-identity.ts:46). At 119,950 rows and 17,877 candidates that is tens of thousands of statements plus git spawns. This repo has a live incident class for exactly this shape: docs/memory.md hard-locks memory-health to tier full after incident #226 promoted its unbounded full-active-memories scans to a 15-min tick, and records a 31.9s event-loop stall plus a 30s vec-search timeout observed on 2026-11-05. Run the apply offline against a stopped daemon or a datadir copy, never against the live process.
- PROD-DATADIR MIGRATION FOOTGUN (fresh, 2026-11-05): per docs/memory.md, any checkout CLI that calls openRuntimeDb() runs migrate() on whatever datadir it opens; doing so applied unreleased 064-cost-ledger.sql to prod, and the pinned release 0.22.1+56e7f4c0 (schema 63) then refused to boot against schema 64, exiting 3 times in 5 minutes. src/cli/repo-identity-backfill.ts:59 calls openRuntimeDb(). Compare the newest migration (currently 064-cost-ledger.sql, 64 files present) against the installed release before pointing the extended backfill at the live datadir.
- OVER-BROAD OVERRIDE CLOBBERING A DELIBERATE LABEL: an override that fires whenever cwd looks like a worktree would discard an intentional project_id a client meant to set. AC-5 bounds the trigger to the case where project_id equals basename(cwd), which is the actual hook behavior, and leaves any other value untouched. Widening that condition later reintroduces the risk.
- PATH LEAKAGE IN LOGS AND PREVIEW OUTPUT: both the override log event and the backfill preview echo filesystem paths embedding the operator's home-directory layout. The repo ships a redaction layer (src/redact/) and a client-scrub wire contract, so emitting raw absolute cwds in daemon logs is inconsistent with that posture. AC-9 constrains both to the derived repo-root basename.

The daemon-side override is explicitly designed not to wait on it, defending against old plugins, so slices 1-4 are unblocked; only the eventual removal of the override is gated.
