## Lessons

- **The real defect this slice taught the wave something about:** `repo-identity-backfill --json`
  printed the result object verbatim, and `candidate.cwd` carried the session's raw absolute
  filesystem path (home-dir-revealing) straight out of the core module — contradicting DEC-017
  rule 3 and the file's own doc comment ("never prints a raw filesystem path"). The original
  self-review and self-validation both passed this slice by verifying the CLI layer through
  *static code reading* ("read every console.log call site individually... not exercised as a
  live CLI scenario... lower-value than core-level coverage already obtained"). That judgment was
  wrong: the leak lived in the *data shape returned to the caller*, not in the CLI's print
  statements, so no amount of reading the print call sites would have found it. It was only caught
  once something actually ran the compiled CLI end-to-end against seeded data and inspected the
  real printed JSON (commit `9f57ae8d`, "fix(slice-445): redact candidate cwd + surface DEC-017
  source field (AC-9)"). Fixed at the source — the candidate record no longer carries `cwd` at
  all, only a `cwdBasename` that is a basename by construction in every branch.
- A second, separate fix pass (commit `4d9b3c1c`) corrected the self-review/self-validation
  artifacts' own prose: they claimed "all 6 original tests pass unmodified in behavior" when the
  base file actually had 7 tests and one (`MIGRATION HAZARD guard`) had its assertions correctly
  *inverted* by DEC-017 rule 4 — a real, intended behavior change that the review text
  mischaracterized as "renamed fields only." Also closed: AC-6 had never actually been
  demonstrated with two consecutive `dryRun: true` calls (the existing "idempotent-second-run"
  tests called `dryRun: false` twice — apply, then apply again — a different property), and AC-8's
  dashboard-dropdown half had no test at all despite being claimed covered. None of these were
  found by the artifacts' own author re-reading their own work; they were found by whatever
  process ran afterward and is described in both addenda only as "independent verifiers."
- Same wave-level dispatch gap as the rest of the wave (`crew:reviewer`/`crew:verifier` could not
  be dispatched independently from inside the Workflow subagent) — but this slice is the clearest
  evidence in the wave for *why* that gap matters: a same-agent self-review signed off on a real
  privacy defect and an unsubstantiated test-coverage claim, both only caught by a later,
  execution-based check.

## Surprises

- The leak was not where the first review looked. A static read-through of the CLI's print
  statements was a reasonable-sounding verification strategy for "no absolute path reaches
  output," but it checks the wrong layer when the data structure handed to the printer already
  contains the path and `--json` prints that structure verbatim — the fix had to happen in the
  core module's return shape, not the CLI's rendering code.

## Followups

- Before SLICE-447 runs `--yes --column all --sessions` against the real production datadir
  (which it did, in the next wave), explicitly re-verify no other output path in this file prints
  a structure it does not fully control the shape of — this slice fixed the one instance found,
  but the review methodology that missed it (static-only, no execution) was not itself changed
  afterward.
- Add a standing rule to this repo's review checklist: a CLI or server surface advertising
  `--json`/structured output must be exercised by actually running the compiled artifact against
  seeded data at least once per review, not verified by reading the print call sites alone —
  this is the second time in this wave (SLICE-448 is the first) that a real defect survived a
  code-reading-only review and was only caught by something that actually executed the code.
- Carry forward the explicitly-disclosed residual gap: no automated test exercises
  `repoIdentityBackfillCommand` end-to-end because it opens the real runtime DB with no injection
  seam; a DB-injectable seam for this and other `src/cli/*.ts` commands is flagged as a
  not-yet-scheduled future slice.

## What went well

The core generalization (repo-only/memories-only → `column: 'repo'|'project'` + `includeSessions`)
correctly implements DEC-017 rule 4's intentional widening for the deleted-worktree-but-trusted-
shape case, verified byte-for-byte against `deriveWorktreeSafeBasename`'s own trust conditions
rather than merely duplicating them without checking for drift. The never-guess boundary (AC-4)
was independently re-verified against a genuinely never-created directory with ENOENT git
failure, not a mocked one. Once both fix passes landed, the full suite reached 35/35 on the
touched file (up from 21/21) with the three real gaps — AC-6's actual property, AC-8's dashboard
half, and the CLI-layer argv tests — closed with real test coverage, and the regression gate
(`env -u ASTRA_SKIP_CONSOLIDATE bun run test`) stayed at the wave's documented 5819-passed/3-known-
flake baseline throughout.

## What went wrong

Two real gaps shipped past the first self-review and self-validation pass and needed a second
fix round to close: an actual home-directory-revealing data leak in `--json` output, and
inaccurate coverage claims in the review/validation prose itself (both of which a from-scratch
independent reviewer, rather than the same agent re-reading its own work, would have had a much
better chance of catching on the first pass).

## What I would do differently next time

Treat "I verified this by reading the code" as insufficient for any claim about what a `--json` or
other machine-readable output surface actually contains — run the compiled artifact once against
a seeded fixture and read the real output, every time such a surface is touched, before writing
the review's verdict.
