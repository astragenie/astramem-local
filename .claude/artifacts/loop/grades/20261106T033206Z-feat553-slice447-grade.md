## Lessons

- **A real production incident occurred during the apply:** one 55-second event-loop stall was
  recorded on the live daemon while the ~17,877-row (combined repo+project) `UPDATE` pass ran
  against the production SQLite datadir. It self-recovered and `doctor`/`/health` came back
  green afterward, but a backfill of this size run against a *live, request-serving* daemon
  blocked the event loop long enough to be user-visible if anyone had been using the daemon at
  that moment. The validation artifact's own write-back explicitly recommends running this kind
  of backfill "in a quiet window" — a mitigation documented after the fact, not built into the
  CLI (no batching/chunking of the UPDATE pass, no daemon-pause step in the runbook).
  Production-readiness score reflects a real operational gap, not a hypothetical one.
  See Followups for the concrete fix recommended for next time.
- **The default `agent-*` regex did not catch every bad project label.** The backfill's default
  pattern (built around `^agent-[0-9a-f]{17}$`-shaped hashes) correctly caught the hash-named
  worktree directories, but real Claude Code worktrees are sometimes named with human-readable
  branch-style slugs (e.g. `agent-l3-4`, plus non-`agent-`-prefixed ones like
  `memoized-jumping-elephant`, `transient-dancing-wren`). These needed a second, manually-
  targeted pass (`--pattern '^agent-l3-4$'`, 7,398 rows) found only because the operator read the
  preview's actual label list rather than trusting the default pattern's row count alone. A
  backfill tool whose "done" signal is a single default-pattern pass would have silently left a
  large resolvable chunk un-fixed.
- The ceremony around a prod-mutating operation (backup-before-apply with verification, two
  preview-only dry-runs proving byte-identical counts before any `--yes`, an explicit operator
  go/no-go step, post-apply counts cross-checked against an independent read-only census) is
  exactly the kind of gate that caught the pattern-coverage gap above in time — the operator's own
  review of the preview output, not an automated check, is what surfaced the `agent-l3-4` and
  branch-slug cases.

## Surprises

- The preview's own "unresolved" counts (1,083 for `repo`, 3,527 for `project` before the second
  targeted pass) were large enough, and intentionally so by DEC-017's never-guess rule, that
  distinguishing "intentionally unresolvable by design" from "resolvable but missed by the
  default pattern" required a human reading actual label text in the preview output — a purely
  numeric dry-run report would not have surfaced the `agent-l3-4` gap.

## Followups

- Chunk or rate-limit the UPDATE pass (or add an explicit "pause ingest / drain queue" step to
  the runbook) so a backfill of this row count cannot produce a multi-second event-loop stall on
  a live daemon again; the current mitigation is "pick a quiet window," which is operator
  discipline, not a structural fix.
- Consider widening the backfill's default label-detection beyond a hex-hash regex (or add a
  "review the top N most common currently-unresolved label strings" prompt to the preview output)
  so a second manual `--pattern` pass isn't the only way human-readable worktree names get caught.
- `docs/memory.md`'s provenance-leak entry was superseded with the final counts per this slice's
  own write-back step — confirm on the next session that it reads as closed, not still "gap."

## What went well

Every production-mutation safeguard this slice's own scope promised was exercised for real, not
simulated: a verified pre-apply backup (`verified: true`, 9.3s), two consecutive dry-run previews
producing byte-identical counts (the AC-6 property), an explicit operator approval step before
any `--yes`, and a post-apply read-only census cross-checked against the reported unresolved
counts (`969 + 854 ≤ 1,083 + 3,493`, confirming AC-8's "remaining == unresolved, no higher"
invariant). Migration-version parity between the checkout CLI and the installed release was
checked before any command touched the datadir, per this repo's own `AGENTS.md` house rule. The
dashboard's project dropdown dropped from 372 to 102 options as a direct, verified consequence.

## What went wrong

No independent review artifact exists for this slice at all (reasonable given it is
docs-only-by-`touches_files` plus a live operational execution, but still a real gap in the
record — there is no second pair of eyes on the runbook text itself, only on its execution). A
real 55-second event-loop stall occurred against the production daemon during the apply, and the
default pattern under-covered real bad data, requiring an ad hoc second pass caught by operator
judgment rather than by the tool's own design.

## What I would do differently next time

Build the "run this in a quiet window" and "manually scan unresolved labels for human-readable
patterns the default regex misses" steps into the runbook and the CLI's own preview output
*before* the live run, rather than discovering both as live findings during the one production
execution this FEAT gets.
