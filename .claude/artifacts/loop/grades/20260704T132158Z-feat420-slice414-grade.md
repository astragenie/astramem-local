## Lessons

- The FEAT's worst-case scenario was REAL: better-sqlite3 silently accepts a
  pre-existing 0-byte datadir as a fresh database and migrate() builds an
  empty schema over it — silent data loss with no error. Found by empirically
  probing corruption scenarios before writing guards.
- SQLCipher cannot distinguish wrong-key from corruption at the driver level
  (both throw SQLITE_NOTADB "file is not a database") — any corruption
  diagnostic in an encrypted product MUST branch on whether a key was in
  play, or it steers operators toward deleting healthy encrypted data.
- Cross-platform blind spot bit twice today (this slice's sibling FEAT-419
  too): all local verification runs on Windows; Linux CI is the only place
  timing/host differences surface. Treat first CI run as part of the test.
- Fixture at reduced embed dim (8 vs 1024) keeps a committed binary at 286KB
  instead of 4MB+ — dim is parameterized (FEAT-409), upgrade realism intact.

## Decisions

### DEC-006: Fail-loud guards branch on key presence

**Rationale**: openDb wraps raw driver errors into typed, actionable errors —
CorruptDatadirError (no key in play: corruption diagnosis, deletion as last
resort) vs EncryptionKeyError (key supplied: wrong/missing-key diagnosis,
secrets.env + stale-global-install checklist, file explicitly left untouched).
One catch-all wrapper was a CRITICAL review finding: it mislabeled recoverable
key problems as corruption.

**Consequences**:
- positive: operators get the right remediation for each failure class; the
  documented v0.3.4-shadowing symptom now produces a self-diagnosing error
- negative: two error types for one driver symptom — callers matching on
  CorruptDatadirError must remember keyed opens throw the other type

### DEC-004: Generator script + frozen binary fixture, cross-checked

**Rationale**: committed generator documents regeneration (future schema
bumps add fixtures by running it); committed binary is the true frozen
artifact; the test asserts generator output matches the committed manifest so
neither can rot silently.

**Consequences**:
- positive: bounded, repeatable fixture maintenance per schema bump
- negative: 286KB binary in the repo; scoped .gitignore exception to maintain

## Surprises

- The 0-byte silent-accept was worse than the FEAT hypothesized — not a
  missing guard on a rare path but the default driver behavior on the main
  open path.

## What went well

Empirical probing before guard-writing found a real silent-data-loss bug.
Review gate caught a CRITICAL operator-safety regression (wrong-key
mislabeled as corruption) that all tests missed — the exact false-positive
class the dispatch flagged as highest-risk. Fix + regression test landed
same-branch within the hour.

## What went wrong

First iteration of the guard shipped the catch-all wrapper despite the
dispatch explicitly warning about the SQLCipher wrong-key symptom — the
warning was in the reviewer's brief but not the builder's. Original reviewer
stalled on the delta pass; orchestrator finished the delta inline per user
instruction.

## What I would do differently next time

Put known false-positive classes in the BUILDER's dispatch too, not only the
reviewer's — cheaper to avoid than to catch.
