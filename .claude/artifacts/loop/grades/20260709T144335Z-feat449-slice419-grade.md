## Lessons
- **Clean, in-scope build (contrast FEAT-441's table overreach).** Tight dispatch guardrails stated up front ("no schema change, no self-HTTP, no stray files") kept the builder in scope; it proactively merged origin/main to build against atom@2 but left the slice work uncommitted per instruction. Front-loading the "do NOT" list works.
- **Verify against git, not the editor index.** The branch-switch + stash dance produced stale cross-branch diagnostics (`loader.ts`/`config.distill` false errors from the unmerged durability branch). `git diff main` + `bun run build` exit 0 were the source of truth; the language-server diagnostics were noise. Don't act on diagnostics alone after a branch switch.
- **Reviewers caught two quality gaps tests didn't**: the boot-time drain was synchronous+unbounded — it would stall the event loop on exactly the large backlog this feature recovers from — and the spool path-key had no defense-in-depth guard. Both cheap to fix, neither would have failed a test.
- **Behavior-preserving hot-path refactor, proven safe**: extracting `ingestCanonicalTranscript()` from the `/ingest/transcript` route was validated by the 59 pre-existing ingest/idempotency tests being byte-identical and green — the right way to de-risk a refactor of a live path.

## Decisions
### DEC-449-1: Spool is a filesystem content queue (not a DB table, not self-HTTP)
**Rationale**: Capture must not depend on daemon availability and must not race worktree cleanup; a filesystem content spool decouples both, with zero schema change (contrast the FEAT-441 table-overreach lesson).
**Consequences**: + survives daemon-down (AC-8), no migration, no self-HTTP hop. − a second drain surface to operate (quarantine dir, counts).

### DEC-449-2: Quarantine by rename, never delete
**Rationale**: A poison/oversize/conflict envelope must stay recoverable on disk for debugging; deletion is data loss.
**Consequences**: + no data loss; reason sidecar auditable. − quarantine dir needs occasional operator attention.

### DEC-449-3: Bounded per-tick drain (maxPerTick=50) + 1s fast re-arm
**Rationale**: One synchronous sweep of a large backlog would stall the single-threaded event loop at boot — the exact scenario this feature recovers from.
**Consequences**: + large backlog drains over bounded ticks, no stall. − a big backlog takes several seconds of wall-clock to fully drain (acceptable).

## What went well
Cohesive spool design, fail-open capture, bounded drain, quarantine-not-delete, redaction preserved, hex-guard. Real-transcript smoke (941KB/62-turn) + 8/8 AC validation gave strong confidence pre-release.

## What went wrong
Branch-switch stash contamination scare cost a detour to disprove (stale diagnostics, not real). Two review-caught gaps (boot-stall, hex-guard) should have been designed in from the dispatch.

## What I would do differently
State the "bounded per-tick / no boot stall" and "guard the path key" constraints in the build dispatch up front, as with the anti-overreach guardrails — reviewers shouldn't have to catch backpressure basics.
