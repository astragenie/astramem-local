## Lessons

- Same wave-level dispatch gap as SLICE-442/443/445/448: `/crew:orchestrate-slice` could not
  dispatch `crew:reviewer`/`crew:verifier` as independent subagents from inside this Workflow
  subagent (no `Agent`/`Task` tool available), so the builder performed both the review and the
  validation itself, disclosed plainly in both artifacts' frontmatter rather than presented as
  independent. The fallback review was still substantive — it independently verified the
  `resolveRepoIdentity`/`resolveRepoIdentityAsync` shared-cache claim by reading
  `repo-identity.ts` rather than trusting the code comment, and traced the `source`-attribution
  judgment call (raw vs. merged repo value) to the one place a mistake there would have silently
  broken the git-vs-string distinction DEC-017 rule 3 needs measured.
- A conservative-by-construction override (equality-gate before any derivation runs, no-op guard
  when the derived value doesn't actually change anything) is a sound design for a daemon-side
  data-correctness fix: it structurally cannot fire on an explicit, deliberate `project_id` label
  (AC-5), which matters more here than maximizing override recall.

## Surprises

- The equality check for "has the client sent a basename, not a real label" had to be built as a
  brand-new helper (`plainBasename`) rather than reusing `deriveWorktreeSafeBasename` from
  SLICE-442 — because `deriveWorktreeSafeBasename` already resolves a worktree path to the REPO
  name, so for the exact AC-1 bug case it could never equal the hook's raw
  `basename "$CWD"` output. Using the more-resolved helper for the equality gate would have made
  the override never fire on the bug it exists to fix — a subtle trap that the review caught by
  reasoning about the two functions' different outputs, not by a failing test.

## Followups

- Non-blocking risk disclosed in review: on an idempotent request replay, the override-detection
  code (and its log line) runs before the `db.transaction()` that would throw
  `IdempotentReplayError`, so a replayed request can double-log an override event even though no
  second DB write happens. Inherited from the pre-existing `sessionRepo` computation's identical
  hoisted-before-tx pattern; fixing it cleanly would need restructuring outside this slice's scope.
  Worth a one-line note before anyone re-derives override-rate metrics from these logs.
- `ASTRA_SKIP_CONSOLIDATE=1` ambient-shell env trap (same as SLICE-442/448) — still not fixed at
  the profile level as of this slice.

## What went well

Exactly the 5 declared `touches_files`, no scope creep (confirmed by `git status --porcelain`
plus a grep for the new function names outside those files). All 3 session-upsert call sites were
wired with the override, matching the slice's own line references. AC-9's "never log a raw path"
requirement is structurally guaranteed, not just tested: every field the logger call can emit is
constrained to a basename by the override's own precondition, so no value of the client's input
can make it emit a path. 78/78 touched-suite tests pass, including the one real-git,
real-linked-worktree canary test that exercises the `'git-common-dir'` source value against
actual git output rather than a hand-constructed stub.

## What went wrong

Nothing code-level; the one disclosed risk (idempotent-replay double-logging) is log-only and
inherited, not introduced by this diff. The same self-review/self-validation process gap as the
rest of the wave applies here too.

## What I would do differently next time

Add a lightweight regression test specifically for the idempotent-replay double-log case flagged
in review, rather than carrying it forward as a disclosed-but-untested risk — it would have taken
one more test and would close the gap instead of just naming it.
