## Lessons

- **A real functional bug shipped past unit tests and the first self-review, and was only caught
  by an adversarial, execution-shaped check.** The agent `<select>` and its free-text `<input>`
  fallback deliberately share `name="agent"` (per the slice's own design). Every original test
  exercised the two controls independently — never the real serialized-together HTML form
  submission a browser actually produces. In a real GET, picking a dropdown option while leaving
  the free-text box at its default blank value serializes as `agent=<picked>&agent=`, and the
  original "last value wins" parsing took the trailing *blank* entry, silently discarding the
  user's selection on the primary, everyday interaction path. 84/84 green tests gave false
  confidence; the defect was only found once something reproduced the actual two-field submission
  via `querystring.parse('agent=crew%3Areviewer&agent=')` against the real function — exactly the
  kind of check an adversarial AC-evidence verifier runs and a happy-path unit test does not.
  Fixed in commit `4b726532` by scanning from the end of the value array for the last
  *non-blank* entry.
- A second fix round (`cd73aad1`) closed two more gaps an independent pass found: the slice's
  declared `touches_files` omitted `src/server/routes/dashboard.ts` even though a real one-line
  change there was required for the feature to work outside of unit tests (which call
  `renderDashboard`/`queryRecentMemories` directly, bypassing the route entirely) — a gap that
  "all tests pass" could not have caught by construction, since the route wiring is exactly what
  the unit tests skip; and AC-4's "zero-match" case (`agent=does-not-exist-anywhere`) had no test
  at all despite being claimed covered.
- Same wave-level dispatch gap as the FEAT-553 slices: no `Agent`/`Task` tool was available to
  dispatch an independent `crew:reviewer`/`crew:verifier`, so both passes were self-review by the
  same agent that wrote the code — disclosed plainly in the review artifact's own frontmatter. Of
  the whole wave, this slice is the strongest evidence that the self-review fallback is not an
  adequate substitute for an independently-dispatched reviewer: a reviewer coming to the diff cold
  is far more likely to actually try the two-field form submission than the implementer who just
  designed the shared-name interaction and is anchored on their own mental model of how it works.

## Surprises

- The bug was invisible at every layer this slice's own test suite checked (pure function calls,
  rendered HTML snapshot assertions) because none of them constructed the actual
  multi-value-same-key query string a real form produces — the gap was in the *test construction
  method*, not in missing an edge case within a correctly-constructed test.

## Followups

- Treat "a form has two controls sharing one `name`" as a standing trigger for a same-name
  multi-value regression test (via `node:querystring` or equivalent, not direct object
  construction) anywhere else in this dashboard that uses the same select+free-text-fallback
  pattern, in case it is reused for the project/profile filters later.
- No live-browser round trip against a running daemon was ever performed for this slice (disclosed
  in the validation artifact as a deferred gap) — worth doing once, even manually, before calling
  a UI-facing filter fully done, since the bug above is exactly the class of defect a 10-second
  manual click-through would have caught on day one.
- Consider splitting the free-text fallback into its own small `<form>` to remove the shared-name
  interaction entirely, rather than relying on "select wins when free-text is blank" as the
  permanent contract (flagged as a non-blocking LOW finding in the review, not yet scheduled).

## What went well

The underlying data/query layer is solid: `queryAgentOptions` rides the existing `idx_memories_agent`
index with a bounded `LIMIT` rather than an unbounded `GROUP BY`, AND-composition into the same
`conditions`/`params` arrays as `project`/`profile` is correct and verified by reading the actual
line numbers, and the XSS-escaping requirement (AC-5) was proven against a real
`<script>`-bearing fixture value, not just asserted. After both fix rounds, all 8 ACs have direct
test evidence and the touched-suite tests are green (89/89 after the fixes, up from the original
84/84 that missed the real-submission case).

## What went wrong

A real, user-facing functional regression (the primary happy-path interaction silently discarding
the user's filter choice) shipped past the original unit test suite and the first self-review
pass. A second gap — an undeclared-but-necessary file in scope, and a missing AC-4 test — also
needed a follow-up fix round. Both gaps share a root cause: the same agent that designed and
built the feature also reviewed and validated it, and its own mental model of "how the shared-name
form behaves" was wrong in a way a fresh reviewer actually exercising the real submission path
was positioned to catch and the implementer was not.

## What I would do differently next time

For any UI control that shares an HTML `name` attribute with another control, write the
regression test as a real serialized-query-string round trip (both controls present, in document
order, including the blank-default case) as the FIRST test written, before any direct-object-
construction convenience tests — this slice wrote the convenience tests first and never came back
to add the real-submission case until an adversarial check forced it.
