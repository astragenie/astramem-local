## Open questions — RESOLVED (lead decision, 2026-07-07)

**Q: install-into-release vs copy prod node_modules?** (the architect decision
FEAT-438 flags)
**A: `bun install --production --frozen-lockfile` executed inside the release
dir**, using the copied package.json + lockfile. Rationale: deterministic via
lockfile; native modules (better-sqlite3/SQLCipher, sqlite-vec) get
platform-correct prebuilds; avoids fragile prod-subset computation from the
checkout's mixed node_modules. The network-dependency downside is mitigated by
bun's local cache and — decisively — by the boot-verify gate: if install
produced a broken tree, boot-verify fails and the release is quarantined, never
served. Copy-from-checkout remains a documented fallback if install proves
flaky in practice (revisit in SLICE-3 if needed).

## Proposed approach

1. `src/service/release.ts`: `materializeRelease(opts) -> { releaseDir, manifest }`
   - resolve pkgversion (package.json) + gitsha (`git rev-parse --short HEAD`;
     tolerate no-git → `nogit` suffix, still functional).
   - build into a temp dir sibling (`releases/.tmp-<id>`), then atomic rename to
     final `releases/<ver>+<sha>` only after boot-verify passes (partial dirs
     never look valid — AC-3 by construction).
   - steps: copy `dist/` + package.json + bun.lock → `bun install --production
     --frozen-lockfile` (spawnSync, capture output) → write `release.json`
     manifest → boot-verify `node <tmp>/dist/cli/index.js --version` (expect
     exit 0 + version match) → rename tmp → final.
   - failure at any step: delete or rename tmp dir to `*.failed`, throw with the
     captured step output.
2. Tests (`tests/service/release.test.ts`): happy-path layout + manifest fields;
   boot-verify executed from outside the checkout; forced-failure path (broken
   package.json) → non-zero, no valid dir, `current.json` untouched.
3. No wiring into `reinstall` yet — export only. SLICE-2 wires + repoints.
